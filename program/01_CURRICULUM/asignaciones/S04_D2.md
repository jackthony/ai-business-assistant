## 5. Contrato (no se negocia)
Todo en inglés (nombres públicos); los textos que vea la clienta no se tocan aquí (los pone el agente).

### 5.1 Verificación (GET)
`verify_challenge(mode: str | None, token: str | None, challenge: str | None, verify_token: str) -> str | None`
- Devuelve `challenge` solo si `mode == "subscribe"`, `token` coincide con `verify_token` (compara con `hmac.compare_digest`) y `verify_token` no está vacío. En cualquier otro caso, `None`.

### 5.2 Firma (POST)
`signature_is_valid(body: bytes, header: str | None, app_secret: str) -> bool`
- La cabecera tiene la forma `sha256=<hex>`: HMAC-SHA256 del **cuerpo crudo** con `app_secret` (no con el verify token).
- Falla cerrado: sin cabecera, sin `app_secret`, sin el prefijo `sha256=` o con otra firma → `False`. Comparación en tiempo constante.

### 5.3 Conversión a evento
`parse_payload(payload: dict, tenant: str = "hola_mujer") -> InboundEvent | None`
- Lee `entry[0].changes[0].value.messages[0]`. El `user_id` es el campo `from` del mensaje; el canal es `"whatsapp"`.
- `type == "text"` → evento `text` con `content = text.body`.
- `type == "audio"` → evento `voice`, `content=None`. `image`, `video`, `document` o `sticker` → evento `media`, `content=None`.
- Devuelve `None` (nunca lanza) si no hay `messages` (por ejemplo solo `statuses`), si el tipo es otro (`reaction`, `location`, desconocido), si falta `from` o si el payload está incompleto o vacío.

### 5.4 Router y proceso en segundo plano
`build_whatsapp_router(graph, verify_token: str, app_secret: str, send_func: Callable[[str, str], Any], tenant: str = "hola_mujer") -> APIRouter`
- `verify_token` o `app_secret` vacío (o solo espacios) → `ValueError`.
- Prefijo `/whatsapp`. `GET /whatsapp/webhook` con los parámetros de consulta `hub.mode`, `hub.verify_token`, `hub.challenge` (necesitas `alias`): si `verify_challenge` devuelve texto → 200 con ese texto **en texto plano**; si no → 403.
- `POST /whatsapp/webhook`: lee el cuerpo con `await request.body()` **antes** de interpretarlo; valida la cabecera `X-Hub-Signature-256`; firma mala o ausente → 403 (y nada se procesa). Con firma buena, JSON no válido → 200 sin procesar. Con firma buena responde **200 de inmediato** `{"ok": true}` y agenda `process_whatsapp_event` con `BackgroundTasks` si `parse_payload` dio un evento.
- `process_whatsapp_event(event: InboundEvent, graph, send_func: Callable[[str, str], Any]) -> None`: llama `handle_inbound(event, graph=graph)` y, si hay respuesta con texto, `send_func(event.user_id, reply.text)`. No importa `sender.py`, no usa red ni tokens: `send_func` llega inyectada.
- El agente no cambia (ADR-011): el hilo sale de `thread_id_for(event)` = `"<canal>:<user_id>"`.

### 5.5 Cableado en `create_chat_app`
Tres parámetros nuevos, opcionales, **después** de los de Telegram y antes de `tenant`: `whatsapp_verify_token: str | None = None`, `whatsapp_app_secret: str | None = None`, `whatsapp_send: Callable[[str, str], Any] | None = None`. Si los tres vienen con valor, se hace `app.include_router(build_whatsapp_router(...))`, paralelo al bloque de Telegram. Los parámetros existentes no cambian de nombre ni de orden relativo.
